# TalkEasy — notes for AI agents / contributors

- Expo SDK 57. Read the versioned docs at https://docs.expo.dev/versions/v57.0.0/ before changing native modules.
- Architecture, schema, navigation and accessibility rules: docs/ARCHITECTURE.md. Follow them.
- Hard rules: no analytics, no accounts, no cloud SDKs, no telemetry. A child's data — practice, recordings, progress, photos, schoolwork — NEVER leaves the device.
- ONE EXCEPTION TO "no network", and it is the only one: `src/subscription/storeProvider.ts` talks to Google Play / StoreKit through `expo-in-app-purchases`, because a subscription cannot be sold without the store. It is confined to that file, reached only through `SubscriptionProvider`, and sees a product id and the store account — never anything about a child. Nothing else in the app may open a socket. Adding a second network caller is a decision to re-make, not a precedent to follow.
- Child-facing controls: tap only, >= 64pt, sized via `useSizes()`. Parent controls >= 56pt.
- Screens never write SQL: screen -> hook -> repository -> SQLite. Emit `notify(topic)` after writes.
- Schema changes are a NEW entry in `src/database/schema.ts` MIGRATIONS; never edit old ones.
- Verify with `npm run typecheck`, `npm run check:db`, `npm run check:learning`, `npm run check:adaptive`, `npm run check:i18n`, `npm run check:speech`, `npm run check:layout`, `npm run check:themes`, `npm run check:practice`, `npm run check:stages`, `npm run check:plus`, `npm run check:therapy`, `npm run check:scan` and `npm run check:headers`.
- Responsive layout is CHECKED, not eyeballed: `check:layout` models every fixed-width row on the child Home screen (the HUD, the hero's two columns, the syllable chips, the explore tiles, the nav cells) at 320/375/390/430pt and at both ends of the OS font scale, and fails if a string cannot fit the room its row leaves or a tap target drops below 44pt. A row that must choose a shape - one HUD line or two, four explore tiles or two - asks `fitFontSize` whether the longest label still fits, never a width constant, because the answer depends on the font scale as much as the screen. Reproduce the rule in the check when you add one.
- Learning content lives in `src/learning/content`; it is code, not DB data. Emoji are the pictures (offline-safe).
- Adventure design system (src/theme/adventure.ts + components/adventure): the child-facing game look. It is applied through the ADVENTURE ZONE, not per screen - ChildScreen (and the home screen) wrap their content in AdventureZone, and the shared components (ScreenContainer, ScreenHeader, Card, BigButton, SectionTitle, EmptyState) read useIsAdventure() and dress themselves accordingly. A new child screen inherits the look for free. Parent Mode builds on ScreenContainer/ScreenHeader WITHOUT the zone and must stay calm and plain, so a child can tell the two apart. Gradients use components/adventure/GradientSurface (react-native-svg) - never add a gradient library. Import GradientSurface/Mascot from their FILES inside components/common, never from the adventure barrel, which imports back into common. Every gradient is skipped in high contrast. Pip the mascot is SVG, not an image asset. Inside the zone the theme is the NIGHT theme (`theme.night`): white text on the space sky and `theme.tint(soft)` returns the SOLID colour, so never draw a `tileInk()` glyph on a `theme.tint()` background there (it vanishes) - use white. Shared game pieces: `GameIcon` (illustrated SVG art, incl. the core Talk cards via `ART_FOR_ICON`), `MissionCard` (list rows), `GameTile` (grid cards), `HeroPanel` (a section's coloured banner), `SectionLabel`, `useCardPalette`; `ChildScreen` takes `art` + `subtitle` for the header. Each falls back to the plain look outside the night theme.
- Adventure THEMES (`src/adventure/themes.ts`, `components/adventure/ThemeArt|ThemeMascot|Artwork` + `components/adventure/art/*`): what each world LOOKS like, split from what it MEANS (worlds.ts owns collectibles and milestones, which are progress). A theme supplies the hero companion, and for each of the seven Home destinations an illustration, a hue and two or three corner marks. THE RULE: screens read a theme, they never name a world - there is no `world.id === 'dinosaurs'` in a screen and no DinosaurHomeScreen, and `check:themes` FAILS on either, on a hard-coded `art=`/`color=` in the Home screen, on two cards in one theme sharing a hue, on a decor icon missing from the glyphmap, and on a themed art name with no drawing behind it. Space's entry is exactly what the screen used to hard-code, so an existing child sees no change. Art is `react-native-svg` drawn in code like every other TalkEasy illustration - never bitmap assets: it stays crisp from 320pt to a tablet, costs no decode or texture memory, and needs no lazy loading because only the active theme renders. New art follows the WorldArt rules (64-unit grid, light from the top-left, outlines in a darker shade of the object's own hue, round and smiling - no teeth, no claws) and composes the shared activity tokens from `art/kit.tsx` (SpeechBubble, Pencil, OpenBook, Ball, WordCards), so a card keeps its job while the character changes. ADDING A THEME = one entry in THEMES + one art module; no screen changes.
- My Day is a LIVE schedule (`src/myday/schedule.ts`, `hooks/useMyDay.ts`, `components/myday/MyDayUpcoming.tsx`): `computeDay(items, now)` is pure and decides NOW / NEXT / "Starts in N minutes" / "It's time!" from Parent Mode → Daily schedule (start, optional end, optional "Let's go" link) and the real clock — never hard-code a time or a message. Untimed steps belong between the timed steps around them. When NOW is finished the schedule advances: the next step becomes NOW (with its countdown) and the one after becomes NEXT. Countdowns are words, never seconds ("Starts in 1½ hours"); NEXT is its own touch target (opens its linked activity), the rest of the card opens My Day. `useNow` re-renders on each minute boundary and on return to the foreground. Done/skipped are per day (`routine_log`, status 'done' | 'skipped'); ticks roll over at the first read on a new day. Only the NEXT dot and the "It's time" bell animate; never the whole card, never a sound. Verify with `npm run check:myday`.
- WIDTH-DERIVED SIZES ARE FLOORED (`MIN_SUPPORTED_WIDTH` in constants/sizes.ts). `useWindowDimensions().width` is NOT always a real number: it reports 0 on the first frame and on the web before the pane has a size. Subtracting padding from that goes NEGATIVE, and a negative size handed to an `<svg>` is invalid — the element draws NOTHING, silently, while the text beside it looks perfectly fine. That is exactly how the three "More to explore" icons vanished: `contentWidth` went negative, `exploreArt` came out as -8, and `<svg width="-8">` rendered an empty 0x0 box that still measured as present in the DOM, which is why it survived several rounds of looking at it. Floor the window width before deriving ANY size from it (`Math.max(MIN_SUPPORTED_WIDTH, width)`), so a degenerate frame lays out as the smallest supported phone instead of an impossible one; the next real measurement corrects it. `Artwork` refuses a non-finite or non-positive size as a last line of defence, and `check:layout` models widths 0/1/120/319 AND asserts the Home screen's own source still applies the floor — a check that only reproduced the arithmetic would keep passing after somebody removed the guard.
- Layout rule for web vs device: never size an ABSOLUTELY positioned box with a percentage (width/height '60%', '100%'). The browser resolves it against the parent's padding box, Yoga (iOS/Android) against the content box, so on a padded card it comes out short on a phone only. Fill with offsets (StyleSheet.absoluteFill) and put any percentage on an in-flow child (see GradientSurface). Don't combine overflow:'hidden' with an iOS shadow on one view — iOS clips the shadow; use a shadow shell around a clipping view. Never declare a component inside another component's render (it remounts every render).
- Choose Your Adventure (`src/adventure/worlds.ts`, `components/adventure/WorldArt|WorldBackground`, `screens/child/ChooseAdventureScreen|CollectionScreen`): four interest worlds (Space, Dinosaurs, Animals, Vehicles). A world changes ONLY the motivation layer — scenery behind child screens, the collectibles, Pip's helmet (Space only) and the Daily Mission artwork — never where activities are. Settings `adventureTheme` ('child' = let the child choose, or a fixed world set in Parent Mode) and `adventureWorld` (the child's pick; '' shows Space and an invitation on Home); resolve with `effectiveWorld()`. Collectibles are DERIVED like badges: five milestones shared by every world (first sound; BA–BU in the Syllables activity; a tracing page; a Daily Mission day; 10 Talk taps), counted from existing tables, nothing stored — so switching worlds never loses progress. No milestone rewards correctness. Never present a world as being "for" a kind of child.
- Talk sentence builder (`src/talk/phraseEngine.ts`, used by `hooks/useSpeak`): a starter tile (phrase ending "...") + the next tile become ONE natural sentence via `generatePhrase` - NEVER concatenate labels ("I want" + "Hungry" was "I want hungry."). A tile's PHRASE is its grammar: FRAMES read it into a role (thing / activity / need / state / feeling / word / sentence) and a complement with its own article and casing ("a snack", "Mom"); STARTERS say the roles they can ("I want" + thing → "I want water.") and any other role falls back to the tile's own sentence ("I am hungry.", "I need the bathroom."). New vocabulary needs no code; a new starter is one STARTERS entry. What is shown is what is spoken. Verify with `npm run check:talk` (every default tile after every starter).
- Free vs TALK EASY PLUS (`src/subscription`, `context/SubscriptionContext`, `screens/parent/PlusScreen|SubscriptionScreen`): TWO plans, and the gating config in `subscription/catalog.ts` is the ONLY place that says what Free includes — screens never name a plan, they ask `can(area, index)`. FOUR gated areas, all of them LEARNING CONTENT: Speech Practice stages, Listen & Talk areas, Writing levels, built-in Lessons. WHAT IS NEVER GATED, and this is a product rule not an oversight: Talk/Communicate (it is the child's VOICE — a child asking for the bathroom must never meet a paywall), Feelings, My Day, all four adventure worlds, Parent Mode, and any lesson a grown-up wrote themselves (`lessons.is_builtin`, `accessToItemOwnAuthored`). The free allowance counts from the START of each area's order, because those lists are ordered developmentally and a scattered free plan teaches nothing in sequence. Status is a RECORD not a boolean (plan + source + productId + expiresAt + verifiedAt) so an expiry can lapse and a dev entitlement (`source: 'mock'`) can never pass for a store one — Parent Mode says so in as many words. Billing is reached ONLY through `SubscriptionProvider`, and `subscription/index.ts` CHOOSES the provider by capability — `storeProvider` when the store SDK is in the build, `mockProvider` otherwise — so a release cannot ship the mock and a developer is not locked out of Expo Go. `mockProvider` sells nothing (`canPurchase: false`) and never claims a store entitlement; never add a fake checkout. THE TWO BILLING MISTAKES THAT COST REAL MONEY, both asserted by `check:plus`: a purchase must be ACKNOWLEDGED (`finishTransactionAsync(purchase, false)`) or Google silently REFUNDS it after three days — and with `consume: false`, because consuming a subscription would let it be bought again; and purchases must be taken from `setPurchaseListener`, not from the `purchaseItemAsync` promise, because renewals and purchases made on another device or after an app kill only ever arrive at the listener. There is NO server-side verification (TalkEasy has no server): the entitlement is confirmed by the store and cached, which is honest for a small paid app and not proof against a rooted device — `storeProvider.ts` documents exactly what to add when there is a backend, and `source`/`verifiedAt` already distinguish a locally-trusted entitlement from a verified one. When the store cannot be reached the CACHED entitlement wins: an offline app must never lock a paying family out because the network is down. The paywall may only promise what is actually gated and must carry no pressure language; `check:plus` fails on either, on a benefit naming something that is free, and on an off-by-one in any allowance. A locked card stays TAPPABLE (it explains Plus) because a card that ignores a child's tap just looks broken to them.
- TalkEasy ICON SET (`src/components/icons`: tokens.ts, routineArt.tsx, TalkEasyIcons.tsx): custom-drawn icons for the things a child's day is made of, replacing the stock Material glyphs that made a carefully-built screen look assembled rather than designed (one was a thin outline, the next a solid shape, the next almost a pictogram). Same 64-unit grid and top-left light as the card art in `adventure/art/kit.tsx`, but FAR less detail — an icon has to survive 24pt, where a third object turns to mush. An icon takes ONE ink colour and derives every layer from it by opacity (`Tone`), which is why the set needs no palette of its own and cannot clash with a card it was not designed for. THE RULE THAT IS EASY TO GET WRONG: the ink is usually WHITE on a saturated card and opacity ADDS light, so a low-opacity shape painted on top of a body does NOT darken it — three icons first came out as featureless white blobs this way. A separation inside a mass must therefore be a GAP (card showing through); anything painted on the body must be BRIGHTER than it; `detail`/`shade` are only for pieces sitting on the card beside the body (cutlery, feet, a tassel). Wiring is in `IconTile`, keyed by the Material icon name ALREADY STORED on the routine step — so the drawn set appears with no migration, nothing a family has arranged is rewritten, and a name the set does not cover keeps its Material glyph, which is what lets a grown-up still pick any icon in Parent Mode. Growing the set = one drawing plus one line in `TALKEASY_ICON_ART`. Never bitmaps.
- THERAPY IS ONE SECTION, NOT TWO. Activities used to carry a 'therapy' CATEGORY with six seeded items behind a filter pill, one tap below the card that opens the real Therapy section — two answers to the same question. Migration 16 retired it: the six TalkEasy shipped are DELETED by name, and anything else still in that category is MOVED to 'exercise', because those were created by a grown-up and a cleanup that silently deleted a family's own work is a bug, not a tidy-up (`check:db` asserts both halves). `ActivityCategory` no longer has 'therapy', which is also what removes it from Parent Mode's category picker, so nothing new can be stranded in a category the screen cannot show; `therapyRepo` falls back to 'exercise' for an unrecognised one. The `therapy_activities` TABLE still exists and still holds every other activity — only the category went. Do not re-add it.
- THERAPY home practice (`src/therapy`, `components/therapy`, `screens/child/therapy`, under Activities): a place to RECORD and encourage practice a child's own therapist has already asked for — never a programme, never an assessment, never a substitute for a physiotherapist or occupational therapist. The code is shaped so it cannot drift into one and `check:therapy` fails the build if it does: NO DOSAGE ANYWHERE (no reps, sets, resistance, added load, stretch angles or hold times — those depend on a particular child and are the therapist's to set), every activity carries its OWN specific safety note (duplicates fail, because a shared note is boilerplate nobody reads), and stretching is `therapistLedOnly` — its content is only ever "as your therapist showed you", and no activity may tell a parent to move a limb FOR the child. The SAFETY NOTICE is a GATE, not a banner: nothing in the section opens until a grown-up has tapped through it (`therapySafetyAcceptedAt`, a date not a flag), and it is dressed as a grown-up's screen so a child cannot tap past it out of habit. `therapy_sessions` records THAT practice happened and nothing else — no quality, no range, no correctness — like every other practice table; Parent Goals therefore shows a COUNT of practices, never a score, a target, a streak or a comparison, and says in as many words that the therapist is the person to talk to about progress. Content is code (`therapy/content.ts`); MY THERAPY DAY shows only `inDailyRoutine` activities — a short routine a family can actually finish, because a day listing all nineteen is a list nobody completes and a list nobody completes makes a parent feel behind. A `therapistLedOnly` activity is NEVER on the routine (a slot saying "stretch every morning" is an instruction, and that instruction is the therapist's to give). Parent Mode → Therapy (`TherapySettingsScreen`) is where goals are chosen, any activity can be switched OFF (`therapyHidden` — expected and normal, since these are general ideas and a real child has a real programme), and the week is reported. Goals narrow the day (`therapyGoals`). Icons are abstract and non-medical, with a faceless figure that never implies how a child moves — a drawn child walking unaided would quietly exclude a family using a walker. An activity may ALSO carry a step-by-step PICTURE (`illustration`, a key resolved in `components/therapy/illustrations.ts`): a bitmap, which is a deliberate exception to "art is drawn in code" because a three-panel sequence showing a movement is not something the icon set was built to draw. Activity screens only — never icons, lists, or anything repeated on one screen. The content carries a KEY and the `require()` lives in React-land, because `check:therapy` runs in Node where an asset import does not resolve; the check asserts the key is registered and the file is on disk. A picture NEVER replaces the written steps: words baked into an image cannot be read aloud, do not grow with the OS font size and are invisible to a screen reader. Size it EXPLICITLY (`width`/`height` from the floored window width) — react-native-web ignores `aspectRatio` here and the picture renders at its full natural height. Free covers Gross Motor and Hand & Fine Motor; the notice, the deferral and the safety notes are NEVER gated.
- ACTIVITY PICTURES (`activities/pictures.ts`, `components/activities/activityPictures.ts`, `assets/activities/`): 19 of the 21 seeded activities in Activities → All carry a bundled 3:2 step-by-step picture on their DETAIL screen (never in the list — a landscape picture does not survive a 64pt thumbnail). Activities are DATABASE ROWS with no stable id, so a picture is found by NAME (lower-cased): a grown-up's own activity with the same name shows it too, and renaming a seeded one drops it back to its icon — nothing breaks. PRIORITY: a photo a grown-up attached (`imageUri`) wins, then the bundled picture, then the icon. "Look at photos" and "Kitchen helper" have none (a Kitchen Helper picture exists in the IBGolden folder but was not supplied). Sized with an explicit width and height from the floored window width, capped at 640pt for tablets. `check:db` fails on a name that is not a seeded activity (a typo would silently never show), a missing or wrong-shaped file, a registry that disagrees with the table, and a photo that stops outranking the picture. Pictures are bitmaps with words baked in: they cannot be read aloud or scaled with the OS font, so the written instructions stay on the screen under them, and `check:db` cannot see what a picture SAYS — read each one before shipping it.
- TRACING MUST NOT SCROLL THE PAGE (`components/adaptive/HandwritingCanvas.tsx`, hosted by `WritingCanvasScreen` for all seven Learn & Trace levels and by `AdaptiveLessonScreen` for writing questions). THE ROOT CAUSE was a `PanResponder` inside a `ScrollView` that would hand the gesture back when asked (the default) with the ScrollView left enabled, so a finger dragged down the canvas scrolled the PAGE. Three layers, each asserted by `check:adaptive` because each can be removed alone without anything failing to compile: (1) the responder REFUSES to give the stroke back (`onPanResponderTerminationRequest: () => false`) and blocks the native responder; (2) the canvas reports `onDrawingChange(true)` at touch-DOWN, before the finger has moved, and the host screen sets `scrollEnabled={!drawing}` on ITS OWN ScrollView — so scrolling is off for exactly the length of a stroke and nothing is disabled permanently; release, cancel AND unmount all report false, so the page can never stay locked (the canvas unmounts mid-stroke when Done is pressed); (3) on the web `touch-action: none` on the canvas ONLY, because a browser decides whether a drag scrolls before any script runs. The SVG has `pointerEvents="none"` so the canvas View is always the touch target and coordinates stay relative to it. A NEW SCREEN HOSTING THE CANVAS MUST DO THE SAME: pass `onDrawingChange` and gate its ScrollView — `check:adaptive` scans every screen for `<HandwritingCanvas` and fails one that does not. Verified by driving real touchstart/touchmove/touchend events at all seven levels: the page scrolls before, is locked (`overflow: hidden`, `touch-action: none`) during the stroke, is restored after, the stroke starts exactly under the finger, and a touch outside the canvas still scrolls. NOT verified: an actual iPhone or Android device (the report came from iOS) — the native half is the responder settings plus `scrollEnabled`, the standard remedy, but it has only been reasoned about there.

- ON WEB, A BARE <svg> PAINTS UNDER AN ABSOLUTELY POSITIONED SIBLING, WHATEVER THE TREE ORDER. Every card that draws a `GradientSurface` (which is absolute) and then an illustration has to put the illustration in a `<View>`, or on web it vanishes under the gradient while the text beside it looks fine — the stat pictures, the trophy on the button and Pip in the Achievements summary all went missing this way and were only found by rendering the screen. iOS and Android paint in tree order, so it cannot be seen there. `check:layout` asserts the wrapper. The same rule decides the order of a backdrop (`GalaxyFooter`): FIRST in the tree, so the content paints over it.
- A SCREEN CAN BE VERIFIED WITHOUT A SCREENSHOT. The browser pane is often hidden, and `screenshot` then times out, but a canvas still draws: clone the screen's DOM with every computed style inlined into an SVG `foreignObject`, draw that on a canvas, POST the PNG to a throwaway loopback helper and read the file. Fonts are not carried (a serif fallback and boxes for icon-font glyphs are artefacts of the method, not bugs); layout, colour, gradients, SVG art and paint order are real. Clone only the visible screen's container, not the whole root — the stack keeps earlier screens mounted and a full-page clone crashes the tool.

- DISCOVERY BADGE (`components/adventure/DiscoveryBadge.tsx`, `badgeGeometry.ts`, `hooks/useReducedMotion.ts`): a floating "New!" sticker on a card's top-right corner, wired from a `badge: 'exploreBadge'` key on the explore entry (a string, so the wording is one edit in `i18n`). - THERAPY PRACTICE TIMER (`therapy/timer.ts`, `hooks/useCountdown.ts`, `components/therapy/TherapyTimer.tsx`): a flexible guide under each activity's picture, defaulting to its `suggestedMinutes` (quick 1/3/5/10/15 plus a 1-30 stepper). - SCAN ASSIGNMENT (`src/scan`, `services/ocr.ts`, `hooks/useScanAssignment`, `screens/child/scan`, entry in School Mode): photograph a worksheet, get the words, correct them, hear them read, keep it. A SCAN IS AN ASSIGNMENT — it is saved into the existing `assignments` table, so it appears under School Mode's "Today's assignments" and opens in `AssignmentDetail` with no second store and no parallel list (which is also why a saved scan defaults its due date to TODAY: that list is "due by today", and a scan with no due date is invisible in the one place a parent looks). ONE STATE MACHINE (`scan/machine.ts`), never a handful of booleans — eleven outcomes including a refused camera and a missing engine, and the boolean version is the one that shows a spinner on top of an error. `scanText` is what the engine READ and is never rewritten (the UPDATE statement deliberately omits it); `description` is what the grown-up corrected it to, so the original is always recoverable. The PARSER classifies and never modifies, and NEVER ANSWERS THE HOMEWORK — it will list the sums, it will not work them out; `canMakeActivity` is a higher bar than `type` because a wrong activity wastes a child's time. MANUAL ENTRY IS REACHABLE FROM EVERY FAILURE and from the intro screen: recognition fails for ordinary reasons (handwriting, a crease, a shadow) and a parent who cannot get the words in has no feature. OCR is on-device ML Kit via `@react-native-ml-kit/text-recognition`, a CLASSIC RN module — availability is probed with `NativeModules.TextRecognition` (never `requireOptionalNativeModule`, which only finds Expo modules, and never by asking the package, whose entry point substitutes a Proxy that THROWS on any access when unlinked). It needs `npx expo run:android` once; in Expo Go and on the web it reports `engineUnavailable` and the UI says so. NO NETWORK, NO KEY, NO BACKEND: the photo never leaves the device, and `check:scan` fails on fetch/http/apiKey in the service and on any log line carrying recognised text. Read Aloud goes through `speakContent`, the shared language-aware path — never a second TTS.
- EVERY SECTION NEEDS A DOOR, AND THE DOOR IS CHECKED (`ROUTES_THAT_NEED_A_DOOR` in `check-headers.ts`). School Mode used to be opened from exactly ONE place in the app — a quiet bar wedged between the Home screen's explore row and the nav — directly below an explore card that already said "School". Two school doors side by side on Home, and the quieter one led to the busier screen. The bar is gone and School Mode now opens from a `MissionCard` at the TOP of the School screen, above the timetable: School Mode is where "I need help" and "Bathroom" live, so it must not sit below the browsing a child would have to scroll past to ask to leave the room. Nothing was merged or deleted — the route, the screen and `schoolModeAtStart` are untouched, and that setting is NOT a door (it decides where the app OPENS, not where a child can go mid-session). The card echoes its destination: the same `art="school"` disc and the same `schoolModeSubtitle` string the School Mode header uses. The check exists because removing that bar would otherwise have stranded the screen — and Scan Assignment with it — silently, with the route still registered and nothing failing to compile. It counts two shapes of door, because the app has two: a literal `navigate('X')`, and a route name in a destination TABLE (`screen: 'School'`, pressed via `go(m.screen)`).
- A SCREEN THAT NAVIGATES MUST DESTRUCTURE `navigation` FROM ITS PROPS. Writing `_props` and then calling `navigation.navigate('Foo')` COMPILES AND RUNS — and does the wrong thing: `navigation` is a DOM global (the browser's Navigation API), so on web the call becomes `navigation.navigate('Foo')` on THAT object, which performs a real document navigation to /Foo. The symptom is a full page reload that lands back on the initial route, with the URL set to the route name and no `pushState` anywhere — and it looks exactly like a broken route, which is how it cost a long debugging session. TypeScript cannot catch it because the global is declared in the DOM lib. If a screen navigates, its signature is `({ navigation }: RootScreenProps<'X'>)`.

- ONE HEADER, AND EVERY SECTION FEEDS IT THE SAME THINGS (`ChildScreen` -> `ScreenHeader`, enforced by `npm run check:headers`). The header was already a single shared component, so screens could not drift by rendering different headers — they drifted by PASSING it different things: Speech Practice gave a title, a subtitle and an illustration, My Collection gave a bare title, and the two looked like different apps built from one component. The standard, set by Speech Practice: a SECTION's own screen passes `title`, a `subtitle` saying what the section is for, and `art` (an illustrated GameIcon, preferred on the night sky) or `emoji` (any Glyph name, including a TalkEasy icon). Deeper screens — one lesson, one activity, one stage — are deliberately exempt: a subtitle there just repeats what the screen above said. `check:headers` scans EVERY `<ChildScreen>` tag in a file, because a screen may also render a detail view, and passes when one of them meets the standard; it also fails a section screen that builds its own `<ScreenHeader>`. Reuse the Home card's own subtitle string where one exists (`questPlaySub`, `questLessonsSub`, ...) so the section screen echoes the card the child just tapped. - Sound Practice (`src/soundpractice`, `screens/child/sound`): a PRACTICE aid, never an assessment. Never score an attempt, never transcribe it, never say a pronunciation is wrong - feedback is always encouraging. The child's recording is a temporary cache file that `useSoundRecorder` deletes after playback; it is never persisted and never referenced in the database (`sound_practice_attempts` deliberately has no audio and no correctness column). Every sound in `soundpractice/content.ts` is LETTER ("G", shown) + PHONEME ("/ɡ/", the target) + EXAMPLE WORD ("Goat"), and they are played by different calls: `playPhoneme` ("Play sound"), `playExampleWord`, `playInstruction`/`playLetterName`. A PHONEME IS ONLY EVER A RECORDING (`assets/audio/speech-practice/en/sounds/<id>.m4a`, key `sound:<id>` in `speechpractice/modelAudio.ts`): never give a voice engine the letter ("gee") or a respelling ("guh" is /ɡə/ - a vowel the child copies). Without a recording `playPhoneme` plays the example word as a marked development fallback ('fallback'); never replace that with a respelling. Any line that is an isolated sound carries `soundId` (VoiceLine / SpeechItem) so it goes through `playPhoneme`. `check:speech` enforces the data.
- Speech Practice (`src/speechpractice`, `components/speech`, `screens/child/speech`): the same rules as Sound Practice, for 20 activities. Content is data; `engine.ts` turns it into six exercise kinds (say / choose / build / story / turns / clap) and ONE screen (`SpeechActivityScreen`) runs them all - add content or an engine case, never a new screen per activity. Wrong taps are never marked wrong (replay, then a 💡 hint); nothing is timed; `speech_practice_events` has no audio and no correctness column. Model audio only through `soundPracticeAudio.playItem`/`playSequence` (practice content is spoken in English). NEVER SEND A RAW SYLLABLE TO TTS: the child sees the display text ("BO"), the engine gets the pronunciation-safe spoken form from `speechpractice/pronunciationDictionary.ts` ("beau", en-US) — one explicit entry per syllable per pronunciation set (en/fil/ceb) with IPA, guide and tested alternatives. Fix a sound by editing its `spoken` there; a grown-up can override it per device in Parent Mode → Pronunciation test (`app_settings.speechPronunciationOverrides`). A syllable with no entry is not spoken (`SpeechItem.strict`). A recording (`modelAudio.ts` / `services/modelRecordings.ts`) still wins if one exists. Words/phrases are spoken as written unless listed in `SPOKEN_OVERRIDES`.
- Speech Practice is a LADDER, not a dashboard (`src/speechpractice/stages.ts`, `screens/child/speech/SpeechPracticeScreen|SpeechStageScreen`): five stages - sounds -> syllables -> words -> phrases -> sentences - each opening to a grid of the activities that practise it. The home screen lists STAGES and must never go back to listing every activity by level; a level is a note for a grown-up about difficulty, and to a child it says nothing about what they are doing. Activities that were never speech production (listening, memory, following directions, vocabulary, social, role play, turn taking) moved to Listen & Talk areas via MOVED_TO_PRACTICE and are surfaced on those area screens - moved, never deleted. A stage may hold activities from BOTH modules, so the practice-module sound ladder lives in these stages and its area is marked ownedElsewhere so the Listen & Talk hub does not list it twice. `check:stages` fails if an activity is in two places or in none, if a stage colour is reused, if the ladder order changes, or if the home screen starts mapping activities again. One colour FAMILY per stage: inside a stage every tile is a shade of it, because twelve saturated tiles was most of what made the old screen noisy. The Sounds stage opens a TARGET JOURNEY (`speechpractice/targets.ts`, `SoundTargetScreen`): pick BA and practise it all the way through on ONE screen - listen, say it, three words, a phrase, a sentence, a small game - with the target at the top the whole time, because that is what makes "what am I practising right now?" answerable. Steps are NOT gates: any step opens in any order, opening one marks it practised (for a child who cannot yet produce the sound, having a go IS the practice), and nothing requires speech. Per-target progress is counted with `distinctItems('sounds', stepItemKeys(id))` - a scoped item key on the existing activity, so no new table and no change to a family's Sound Practice history. The word rung practises the INITIAL CONSONANT, not the exact vowel: English has no tidy child-friendly words for each of /ba/ /bɛ/ /bi/ /bo/ /bu/, so the words are /b/-initial and familiar. `check:stages` asserts each target's phrase and sentence actually contain one of its own words, and that game distractors are not target words.
- Voice & Communication (`src/practice`, `components/voice`, `screens/child/voice`, Parent Mode -> `VoicePracticeSummaryScreen`): what a voice DOES in a conversation - pitch, loudness, speed, which word carries the weight, whose turn it is - as listening AND speaking. ELEVEN areas, 52 activities, ten exercise kinds (listen-choose / voice-try / focus-say / turn-light / exchange / wait-go / beat / copy-action / say-more / arrange), ONE screen running all of them. The areas are ORDERED developmentally and check:practice asserts it: attention and early communication and understanding all come before expressive language, and the Speech Sounds ladder runs listen -> sound -> syllable -> word -> phrase -> sentence -> chat with listening first. A theme may dress a prompt ("Your dinosaur's turn!" via the theme's companion noun) but never change an exercise; add content or a kind, never a screen per activity. Same rules as Sound and Speech Practice, and `check:practice` enforces them: nothing is ever marked wrong (a tap that was not expected replays the model and invites another go), EVERY exercise is completable without speaking (`voiceOptional` - the children this section is for are the ones who may not be able to produce the target), `voice_practice_events` has no audio and no correctness column, and a banned-word list keeps clinical language out of every `vc*` string and out of content.ts (a word is allowed only where it is being DENIED, e.g. "not an assessment"). THE APP NEVER ANALYSES THE CHILD'S VOICE: there is no pitch detection and no comparison against the model, so the progress bars show COVERAGE (activities tried / activities in the area), never quality. Two content rules that would otherwise be false: never teach that a question rises (English questions often do not), and never tie one pitch pattern to one fixed feeling. Models are synthesised by `voiceShape.ts` (pure, no react-native - the checks import it) splitting a sentence into segments with their own pitch, because expo-speech has no pitch contour; that makes them approximations, and a recorded `line.audio` always wins. `speakSegments` in services/speech.ts is the only awaited, per-segment TTS path - `speak` resolves immediately and cancels the previous utterance, which is right for Talk and wrong for building a contour.
- CONTENT LANGUAGE is not the app language (`services/contentLanguage.ts`, `voiceCatalog.ts`, `speakText`/`speakContent` in services/speech.ts). The interface is English-only; the schoolwork is not. A lesson STATES the language it is written in (`lessons.language`, '' = English) and everything it speaks inherits that — title, explanation, each vocabulary word, questions, hints. NEVER guess a language from the text: guessing is how "Mga hayop" got read out as the letters M-G-A. Before speaking, the DEVICE is asked which voice it really has (`voiceFor`) — asking an engine for 'fil-PH' is a request, not a guarantee, and engines name the language differently ('fil-PH', 'fil_PH', 'tl-PH'), so matching is by SUBTAG. A real voice is named EXPLICITLY and reads the text as written; when the device has none, the app's own voice reads a pronunciation-safe respelling (`FILIPINO_FALLBACK_LEXICON`) and the `[voices]` dev log says which of the two happened — a fallback is never passed off as a Filipino voice. Display text never changes. Two lexicons on purpose: the GLOBAL one is applied to every English-voice utterance so it may only hold distinctive words (the kinship terms), while the FILIPINO FALLBACK is scoped to Filipino content and so can carry "ang", "sa" and "ano", which applied app-wide would mangle English. A lesson's language travels through BOTH write paths — `lessonsRepo` and `database/seed.ts` — the seed's own INSERT omitting it is what made a freshly installed Filipino lesson speak English. Verified by `check:i18n` and `check:db`.
- Filipino words spoken by an ENGLISH voice ("Ate" → English "ate") are respelled in `services/pronunciationLexicon.ts` ("Ate" → "ah-teh"), applied inside `speak()` for every English-voice utterance; display text never changes. Add a word there (use `caseSensitive` when it is also an English word). Verified by `check:i18n`.
- Localization: TalkEasy is ENGLISH-ONLY — US English (`en-US`, the default, defines the string keys) plus UK, Australian and New Zealand English (`locales/englishVariants.ts`: Commonwealth spelling, "Mum", each its own voice accent). - Tracing guides carry STROKE ORDER arrows (`src/adaptive/strokeOrder.ts` + `components/adaptive/StrokeArrows.tsx`): the handwriting-worksheet convention - the traced letter is drawn HOLLOW (outlined, not filled), with a dashed centre path along each stroke, a small numbered circle where it starts and arrowheads along the way (a second head part-way through a long stroke). Letter coordinates are normalised (x = 0..1 of the glyph advance, y = 0 at cap top and 1 at the baseline) and mapped through `CAP_HEIGHT`, so one table serves every text size; lines and shapes reuse the exact coordinates their guide is drawn with. Numbering restarts per letter. Add a traced character = add its strokes here - `check:adaptive` fails if a level traces a character with no stroke order, and re-measures CAP_HEIGHT against the "H" outline so regenerating the font cannot silently move every arrow.
- Handwriting letterforms are a LANGUAGE setting, not a global one. `locale.letterStyle` picks them: 'single-storey' (the school-print "a" — a circle and a stem, from `SINGLE_STOREY_A` — which EVERY current locale uses, because that is how a child is taught to WRITE the letter) or 'standard' (Nunito's ordinary double-storey "a", used by none). This is handwriting, not typography: it changes the tracing guide and the model letter above the canvas only, never the app's text. The school-print "a" carries its own stroke order too (`SINGLE_STOREY_A_STROKES` via `strokesFor(ch, letterStyle)`), because a circle-plus-stem is not written in the order a bowl-plus-stem is. Only "a" ever differs; never change another glyph. The tracing guide draws outlines from `src/adaptive/schoolGlyphs.ts` via `layoutSchoolText(..., letterStyle)`; the model letter above the canvas is RN text and picks `Fonts.schoolBlack` vs `Fonts.black`. Regenerate outlines with the script noted in assets/fonts/README.md; keep the family name off "Nunito" (OFL reserved name).
